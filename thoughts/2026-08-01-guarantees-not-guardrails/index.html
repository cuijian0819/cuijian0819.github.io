Guarantees, not guardrails

Agent security should constrain what an agent can do, even when untrusted content persuades it to act against our intentions.

In our work on multi-tool agents, the attack begins with a tool provider advertising a capability that sounds genuinely useful, more precise data or a better result, so the model comes to depend on it, and from there the tool can hijack the control flow to harvest or pollute what passes through. What makes this hard is that the model is arguably behaving correctly: if a tool really does offer more precise information, calling it is the right decision. That is why I have stopped treating prompt injection as a category with a clean boundary. There is no reliable distinction between an injected instruction and legitimate information arriving from an external source, and alignment can raise the odds that a model notices, but it cannot guarantee it. Worse, we often want external content to influence behaviour, since ignoring it defeats the point of giving an agent tools at all. So the useful question is not how to detect the bad instruction, because in the general case that detection is not decidable.

The analogy I keep returning to is the phishing email with a malicious attachment. You should absolutely teach people not to open it, and that work is worth doing, but the reason modern systems survive is that the machine assumes the attachment will sometimes be opened and then constrains what it can reach: no sensitive files, no outbound connections. Agents need the same shift, from filtering the input to providing guarantees on the action space, which is what usage control for agentic systems means to me: a policy that holds regardless of what the model was persuaded to believe. That reframing suggests two concrete moves. Stop handing web agents raw click and type primitives, and instead expose higher-level actions defined by the site’s own developer, so that “search for a flight” becomes one auditable operation a user can see and authorise rather than a hundred opaque clicks. And for coding agents, which write and execute a great deal of Python, have the code carry a proof of the security properties we care about, checked before it is translated down to the code that actually runs. In both cases the model stays untrusted, and the guarantee lives somewhere it cannot argue with.
